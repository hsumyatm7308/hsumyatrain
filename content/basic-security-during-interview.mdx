AI နဲ့ Code ရေးပါများလာတဲ့နောက် Basic Security တွေကို တကယ်နားလည်သေးရဲ့လား?

မင်းက Interview အခန်းထဲမှာ ဆိုပါစို့။

CSRF, CSP, SSRF, JWT, CORS, SQL Injection, XSS စသည်ဖြင့် အဲ့တာတွေက ဘာတွေလဲ၊ ဘယ်လိုကွာခြားလဲဆိုပြီး မေးလာခဲ့မယ်ဆိုရင် ရုတ်တရက်ဖြေနိုင်လား။

သိကြတဲ့အတိုင်းပဲ AI နဲ့ Code ရေးပါများတဲ့အခါကျတော့ အခုနောက်ပိုင်း AI Model တွေကလည်း ဒီ Basic Security တွေကို ထည့်ရေးပေးလာကြတယ်။

အဲ့တော့ ကိုယ်တိုင်က သိပ်ပြီး ဂရုမပြုမိတော့ဘူး။

အဲ့ဒီအသုံးအနှုန်းတွေကို မြင်လေ့ရှိတယ်။ Code ထဲမှာလည်း တွေ့ဖူးတယ်။ ဒါပေမဲ့ တကယ် တိတိကျကျ တစ်ယောက်ယောက်က မေးလာပြီဆိုရင် ချက်ချင်း မဖြေနိုင်တာမျိုး ဖြစ်တတ်တယ်ပေါ့နော်။

အမှန်က မသိတာတော့ မဟုတ်ဘူး။ အကြမ်းဖျင်း သိတယ်။ ဒါပေမဲ့ ဦးနှောက်ကို အလုပ်သိပ်မပေးဘဲ AI ကိုပဲ ရေးခိုင်းတာများသွားတော့ ဝေတေဝါးတား ဖြစ်သွားတာ။

ဒါကြောင့် ကိုယ်တိုင်လည်း ပြန်နွှေးရင်း technical terms တွေလျော့ပြီး concept တွေကိုပဲ နားလည်လွယ်အောင် ရိုးရိုးရှင်းရှင်းလေး ပြန်ရေးကြည့်ဖြစ်တယ်။

သိပြီးသားတွေလည်း ပါသလို အသစ်သိလာတဲ့ ဟာတွေလည်း ပါတာကြောင့် စီနီယာများအနေနဲ့လည်း မှားနေတဲ့အရာတွေကို ထောက်ပြပေးသွားလို့ရပါတယ်ဗျ။

ကျေးဇူးပါ။ 





## 1. SQL Injection
SQL Injection ကတော့ Database နဲ့ဆိုင်တဲ့ တိုက်ခိုက်နည်းတစ်မျိုးပဲ။

ဥပမာ Website တစ်ခုမှာ Login ဝင်ဖို့ Username နဲ့ Password ထည့်ရတယ်ဆိုပါစို့။ ပုံမှန်ဆို Website က ထည့်လိုက်တဲ့ Username နဲ့ Password မှန်မမှန် Database ထဲမှာ သွားစစ်ပေးတယ်။

ဒါပေမဲ့ Website ရဲ့ Security က မကောင်းဘူးဆိုရင် Attacker က Username နေရာမှာ ပုံမှန်စာသားအစား Database ကို လှည့်စားနိုင်တဲ့ စာသားတချို့ ထည့်လိုက်နိုင်တယ်။

အဲ့ဒီအခါ Database က အဲ့စာသားတွေကို သာမန် User Input လို့ မမြင်တော့ဘဲ အမိန့်တစ်ခုလို သဘောထားပြီး လုပ်ဆောင်မိနိုင်တယ်။

အကျိုးဆက်ကတော့ Password မသိဘဲ Login ဝင်နိုင်တာ၊ တခြားသူတွေရဲ့ Data တွေကို ကြည့်နိုင်တာ၊ ပြင်နိုင်တာမျိုးတွေ ဖြစ်သွားနိုင်တယ်။
### ဘယ်လိုကာကွယ်မလဲ?
User ထည့်လိုက်တဲ့စာသားနဲ့ Database ကို ပေးမယ့်အမိန့်ကို သီးခြားခွဲထားရမယ်။ (Prepared Statements)
User Input တွေကို သတ်မှတ်ထားတဲ့ပုံစံအတိုင်း ဟုတ်မဟုတ် စစ်ပေးရမယ်။ ( Input Type, Length ) 
Database ကို လိုအပ်တဲ့ လုပ်ပိုင်ခွင့်လောက်ပဲ ပေးထားရမယ်။ ( Least Privilege ) 
Error တက်တဲ့အခါ Database ရဲ့ အတွင်းပိုင်းအချက်အလက်တွေကို User ဆီ မပြသင့်ဘူး။

အလွယ်မှတ်ရရင် SQL Injection ဆိုတာ User ထည့်တဲ့စာသားကို Database က အမိန့်တစ်ခုလို မှားယွင်းပြီး လုပ်ဆောင်မိတာပဲ။

## 2. CORS (Cross-Origin Resource Sharing)
CORS ကတော့ Website တစ်ခုရဲ့ Data တွေကို တခြား Website တွေကနေ ဖတ်ခွင့်ရှိမရှိ ထိန်းချုပ်ပေးတဲ့ Browser ရဲ့ Security စနစ်တစ်ခုပဲ။

ဥပမာ မင်းက ဘဏ် Website တစ်ခုမှာ Login ဝင်ထားတယ်ဆိုပါစို့။ အဲ့ဒီအချိန်မှာ တခြား မသမာတဲ့ Website တစ်ခုကို ဝင်မိတယ်။

အဲ့ Website က မင်း Login ဝင်ထားတဲ့ ဘဏ် Website ဆီ Request ပို့ပြီး Account Information တွေကို ယူဖို့ ကြိုးစားနိုင်တယ်။

ဒါပေမဲ့ ဘဏ် Website က အဲ့ဒီ မသမာတဲ့ Website ကို CORS ခွင့်မပြုထားဘူးဆိုရင် Browser က ပြန်လာတဲ့ Data တွေကို အဲ့ Website ရဲ့ Code က ဖတ်လို့မရအောင် တားပေးတယ်။

ဒီနေရာမှာ မှတ်ထားဖို့က CORS က Request ပို့တာအားလုံးကို တားပေးတာ မဟုတ်ဘူး။ Browser က ပြန်လာတဲ့ Response ကို ဖတ်ခွင့်ရှိမရှိ ထိန်းပေးတာ အဓိကပဲ။
### ဘယ်လိုကာကွယ်မလဲ?
ကိုယ့် Data ကို ဖတ်ခွင့်ပေးချင်တဲ့ Website တွေကိုပဲ သတ်မှတ်ပေးရမယ်။
ဘယ်လို Request အမျိုးအစားတွေကို ခွင့်ပြုမလဲ ကန့်သတ်ထားရမယ်။
Login ဝင်ထားတဲ့ User တွေအတွက် တခြား Security စနစ်တွေကိုလည်း ထပ်သုံးရမယ်။

ဥပမာ - Access-Control-Allow-Origin: https://your-site.com

ဆိုရင် Browser ကို ဒီ Website ကနေ Response ဖတ်ခွင့်ပေးထားတယ်လို့ ပြောတာပဲ။

CORS ကို အလွယ်မှတ်ရရင် ကိုယ့် Website ရဲ့ Data ကို တခြား Website တွေက ဖတ်ခွင့်ရှိမရှိ စည်းကမ်းသတ်မှတ်ပေးတာပဲ။

## 3. JWT (JSON Web Token)
JWT ကိုတော့ Digital ID Card တစ်ခုလို မြင်ကြည့်လို့ရတယ်။

ဥပမာ မင်းက ပွဲတစ်ခုကို သွားတယ်ဆိုပါစို့။

ဝင်ပေါက်မှာ မင်းဘယ်သူလဲဆိုတာ စစ်ပြီး ဝင်ခွင့်ကတ်တစ်ခု ထုတ်ပေးလိုက်တယ်။

အဲ့ဒီကတ်မှာ မင်းရဲ့ ID, ဘယ်နေရာတွေကို ဝင်ခွင့်ရှိလဲ၊ ဘယ်အချိန်အထိ သုံးလို့ရမလဲဆိုတဲ့ အချက်အလက်တွေ ပါတယ်။

နောက်တစ်ခါ ပွဲအတွင်းက သီးသန့်အခန်းတစ်ခုကို ဝင်ချင်ရင် မင်းရဲ့ ဝင်ခွင့်ကတ်ကို ပြလိုက်ရုံပဲ။

JWT ကလည်း အဲ့ဒီသဘောတရားနဲ့ ဆင်တူတယ်။

Website မှာ Login ဝင်လိုက်တဲ့အခါ Server က JWT Token တစ်ခု ထုတ်ပေးနိုင်တယ်။

အဲ့ဒီ Token မှာ User ID, Role, သက်တမ်းကုန်မယ့်အချိန် စတဲ့ အချက်အလက်တွေ ပါနိုင်တယ်။

Token ကိုလည်း Server ဘက်က Digital Signature ထိုးပေးထားတယ်။

အဲ့ဒီ Signature ကြောင့် Token ထဲက အချက်အလက်တွေကို တစ်ယောက်ယောက်က ပြင်ထားလား၊ ယုံကြည်ရတဲ့နေရာက ထုတ်ပေးထားတာ ဟုတ်မဟုတ် စစ်လို့ရတယ်။

နောက်ပိုင်း User က Website ထဲမှာ တစ်ခုခုလုပ်ချင်လို့ Request ပို့တဲ့အခါ JWT ကိုပါ ပို့ပေးတယ်။

Server က Token မှန်မမှန်၊ သက်တမ်းကုန်ပြီလား၊ လုပ်ပိုင်ခွင့်ရှိလားဆိုတာ စစ်ပြီးမှ ခွင့်ပြုမလား ဆုံးဖြတ်တယ်။

ဒါပေမဲ့ တစ်ယောက်ယောက်က Valid ဖြစ်နေတဲ့ Token ကို ခိုးယူနိုင်ခဲ့ရင် အဲ့ဒီ Token ကို အသုံးချနိုင်တဲ့ အန္တရာယ်ရှိတယ်။
### ဘယ်လိုကာကွယ်မလဲ?
Token က တကယ်ယုံကြည်ရတဲ့ Server က ထုတ်ပေးထားတာ ဟုတ်မဟုတ် စစ်ရမယ်။
Token သက်တမ်းကို အရမ်းမရှည်အောင် သတ်မှတ်ထားရမယ်။
Token တွေကို အလွယ်တကူ ခိုးယူလို့မရအောင် လုံခြုံစွာ သိမ်းဆည်းရမယ်။
HTTPS ကို သုံးရမယ်။
Token ကို Sign လုပ်တဲ့ လျှို့ဝှက် Key တွေကို Server ဘက်မှာပဲ လုံခြုံစွာ သိမ်းထားရမယ်။

JWT ကို အလွယ်မှတ်ရရင် Server က စစ်ဆေးအတည်ပြုနိုင်တဲ့ Digital ID Card တစ်ခုလိုပဲ။

## 4. CSP (Content Security Policy)
CSP ကိုတော့ Website တစ်ခုရဲ့ Security Guard လို့ မြင်ကြည့်လို့ရတယ်။

ဥပမာ မင်းရဲ့ Website မှာ Image တွေ၊ JavaScript တွေ၊ Font တွေ၊ တခြား Website တွေနဲ့ ချိတ်ဆက်တာတွေ ရှိတယ်ဆိုပါစို့။

ပုံမှန်ဆို Website က အဲ့ဒီအရာတွေကို အသုံးပြုပြီး အလုပ်လုပ်နေတာပဲ။

ဒါပေမဲ့ Attacker က Website ရဲ့ အားနည်းချက်တစ်ခုခုကို အသုံးချပြီး မသမာတဲ့ JavaScript တစ်ခု ထည့်နိုင်ခဲ့တယ်ဆိုပါစို့။

အဲ့ဒီ Script က User ရဲ့ Information တွေကို ခိုးယူဖို့၊ တခြား Website ဆီ ပို့ဖို့ ကြိုးစားနိုင်တယ်။

ဒီလိုအခြေအနေမျိုးမှာ CSP က အကူအညီပေးနိုင်တယ်။

ဥပမာ Security Guard ကို

"ဒီ Website ကလာတဲ့ Script တွေကိုပဲ ခွင့်ပြုမယ်။ မသိတဲ့နေရာက Script တွေကို ခွင့်မပြုဘူး။ Data ပို့တာကိုလည်း သတ်မှတ်ထားတဲ့နေရာတွေဆီပဲ ခွင့်ပြုမယ်။"

ဆိုပြီး စည်းကမ်းသတ်မှတ်ပေးထားသလိုပဲ။

Browser က အဲ့ဒီစည်းကမ်းအတိုင်း လုပ်ဆောင်ပေးတယ်။
### ဘယ်လိုကာကွယ်မလဲ?
Website ရဲ့ Response Header မှာ CSP သတ်မှတ်ပေးနိုင်တယ်။

Content-Security-Policy:

default-src 'self';

script-src 'self';

img-src 'self' https:;

connect-src 'self' https://api.example.com;



ဒီမှာ

default-src 'self' — အခြေခံအားဖြင့် ကိုယ့် Website က Resource တွေကိုပဲ ခွင့်ပြုမယ်။

script-src 'self' — JavaScript တွေကို ကိုယ့် Website ကနေပဲ ခွင့်ပြုမယ်။

img-src — Image တွေကို ဘယ်နေရာကနေ ယူလို့ရမလဲ သတ်မှတ်တယ်။

connect-src — ဘယ် Server တွေဆီ ချိတ်ဆက်ခွင့်ရှိမလဲ သတ်မှတ်တယ်။

ဒါပေမဲ့ CSP ရှိတာနဲ့ Website က လုံးဝ Safe ဖြစ်သွားတာတော့ မဟုတ်ဘူး။ တခြား Security ကာကွယ်မှုတွေလည်း လိုသေးတယ်။

CSP ကို အလွယ်မှတ်ရရင် Website ထဲမှာ ဘယ်အရာတွေကို Load လုပ်ခွင့်၊ ချိတ်ဆက်ခွင့်ပေးမလဲဆိုတာ စည်းကမ်းသတ်မှတ်ပေးတဲ့ Security Guard လိုပဲ။

## 5. XSS (Cross-Site Scripting)
XSS ကတော့ Attacker က Website တစ်ခုထဲမှာ မသမာတဲ့ JavaScript Code တွေ ထည့်ပြီး တခြား User တွေရဲ့ Browser မှာ အလုပ်လုပ်စေတဲ့ တိုက်ခိုက်နည်းတစ်မျိုးပဲ။

ဥပမာ Website တစ်ခုမှာ Comment ရေးလို့ရတဲ့နေရာ ရှိတယ်ဆိုပါစို့။

ပုံမှန်ဆို User တွေက Comment ရေးတယ်။ Website က အဲ့ဒီ Comment တွေကို တခြား User တွေ ဖတ်လို့ရအောင် ပြန်ပြပေးတယ်။

ဒါပေမဲ့ Website ရဲ့ Security က မကောင်းဘူးဆိုရင် Attacker က Comment နေရာမှာ ပုံမှန်စာသားအစား မသမာတဲ့ JavaScript Code တစ်ခု ထည့်လိုက်နိုင်တယ်။

အဲ့ဒီ Comment ကို တခြား User တစ်ယောက်က ဝင်ဖတ်တဲ့အခါ Website က အဲ့ဒီ Code ကို သာမန်စာသားလို မပြဘဲ Browser မှာ အလုပ်လုပ်သွားစေနိုင်တယ်။

အဲ့ဒီအခါ Attacker ရဲ့ Code က User ရဲ့ Login Information တွေကို ခိုးယူဖို့၊ Website ပေါ်မှာ User မသိဘဲ တစ်ခုခုလုပ်ဖို့၊ တခြား မသမာတဲ့ Website ဆီ လမ်းကြောင်းပြောင်းပို့ဖို့ ကြိုးစားနိုင်တယ်။

ဒီနေရာမှာ မှတ်ထားဖို့က XSS က Server ကို တိုက်ရိုက်တိုက်ခိုက်တာထက် Website ကို အသုံးပြုနေတဲ့ User ရဲ့ Browser မှာ မသမာတဲ့ Code အလုပ်လုပ်သွားစေတာပဲ။
### ဘယ်လိုကာကွယ်မလဲ?
User ထည့်လိုက်တဲ့ Data တွေကို Website ပေါ် ပြန်ပြတဲ့အခါ JavaScript Code အဖြစ် အလုပ်မလုပ်နိုင်အောင် သင့်တော်တဲ့ Output Encoding လုပ်ပေးရမယ်။
User Input ထဲမှာ HTML ထည့်ခွင့်ပေးထားရင် အန္တရာယ်ရှိတဲ့ HTML နဲ့ Attribute တွေကို ဖယ်ရှားပေးရမယ်။ (HTML Sanitization)
innerHTML လိုမျိုး HTML ကို တိုက်ရိုက်ထည့်တဲ့ နည်းလမ်းတွေကို မလိုအပ်ဘဲ မသုံးသင့်ဘူး။
CSP ကို ထပ်မံအသုံးပြုပြီး မသမာတဲ့ Script တွေ အလုပ်လုပ်နိုင်ခြေကို လျှော့ချရမယ်။
Login Session တွေအတွက် အသုံးပြုတဲ့ Cookie တွေကို JavaScript က ဖတ်လို့မရအောင် HttpOnly သတ်မှတ်ထားသင့်တယ်။

အလွယ်မှတ်ရရင် XSS ဆိုတာ Website ထဲကို မသမာတဲ့ Code ထည့်ပြီး တခြား User ရဲ့ Browser မှာ အလုပ်လုပ်သွားစေတာပဲ။

## 6. CSRF (Cross-Site Request Forgery)
CSRF ကတော့ User တစ်ယောက် Login ဝင်ထားတဲ့ Website တစ်ခုမှာ သူမသိဘဲ Request တစ်ခု လုပ်ဆောင်မိအောင် လှည့်စားတဲ့ တိုက်ခိုက်နည်းတစ်မျိုးပဲ။

ဥပမာ မင်းက ဘဏ် Website တစ်ခုမှာ Login ဝင်ထားတယ်ဆိုပါစို့။

Login ဝင်ပြီးတဲ့အခါ Browser ထဲမှာ Session Cookie တစ်ခု သိမ်းထားတယ်။

အဲ့ဒီ Cookie ကြောင့် ဘဏ် Website က နောက်ထပ် Request တွေ ရောက်လာရင် မင်း Login ဝင်ထားတဲ့ User ဆိုတာ သိနိုင်တယ်။

အဲ့ဒီအချိန်မှာ မင်းက တခြား မသမာတဲ့ Website တစ်ခုကို ဝင်မိတယ်ဆိုပါစို့။

အဲ့ဒီ Website က မင်းမသိဘဲ ဘဏ် Website ဆီ ငွေလွှဲဖို့ Request တစ်ခု ပို့အောင် ကြိုးစားနိုင်တယ်။

Browser က အခြေအနေပေါ်မူတည်ပြီး ဘဏ် Website ရဲ့ Session Cookie ကို အဲ့ဒီ Request နဲ့အတူ အလိုအလျောက် ထည့်ပို့မိနိုင်တယ်။

ဘဏ် Website က Cookie ကိုပဲ အားကိုးပြီး Request ကို ယုံကြည်လိုက်မယ်ဆိုရင် မင်းကိုယ်တိုင် ငွေလွှဲခိုင်းလိုက်သလို ဖြစ်သွားနိုင်တယ်။

ဒီနေရာမှာ မှတ်ထားဖို့က Attacker က မင်းရဲ့ Password ကို သိဖို့ မလိုဘူး။ Session Cookie ကို ခိုးယူထားဖို့လည်း မလိုဘူး။

မင်း Login ဝင်ထားတဲ့ အခြေအနေကို အသုံးချပြီး မင်းမလုပ်ချင်တဲ့ Action တစ်ခု လုပ်ဆောင်သွားအောင် လှည့်စားတာပဲ။
### ဘယ်လိုကာကွယ်မလဲ?
အရေးကြီးတဲ့ Request တွေအတွက် CSRF Token သုံးပြီး Request က တရားဝင် Website ကနေ လာတာ ဟုတ်မဟုတ် စစ်ပေးရမယ်။
Session Cookie တွေမှာ SameSite=Lax သို့မဟုတ် SameSite=Strict သတ်မှတ်ပြီး တခြား Website တွေကနေ Cookie ပါသွားနိုင်ခြေကို ကန့်သတ်ရမယ်။
အရေးကြီးတဲ့ Request တွေအတွက် Origin Header ကို စစ်ဆေးနိုင်တယ်။
Data ပြောင်းလဲတဲ့ Action တွေကို GET Request နဲ့ မလုပ်သင့်ဘူး။
ငွေလွှဲတာ၊ Password ပြောင်းတာလို အရေးကြီးတဲ့ Action တွေအတွက် Password ပြန်တောင်းတာ၊ ထပ်မံအတည်ပြုခိုင်းတာမျိုး လုပ်သင့်တယ်။

ဒီနေရာမှာ CORS နဲ့ CSRF ကိုလည်း မရောသင့်ဘူး။

CORS က တခြား Website ကနေ Response ကို ဖတ်ခွင့်ရှိမရှိ ထိန်းပေးတာ အဓိကဖြစ်ပြီး CSRF ကတော့ Login ဝင်ထားတဲ့ User အဖြစ် မလိုလားတဲ့ Request တွေ လုပ်ဆောင်မိသွားတာနဲ့ ဆိုင်တယ်။

ဒါကြောင့် CORS သတ်မှတ်ထားရုံနဲ့ CSRF ကို အပြည့်အဝ ကာကွယ်ပြီးသား မဖြစ်ဘူး။

CSRF ကို အလွယ်မှတ်ရရင် User Login ဝင်ထားတဲ့ အခြေအနေကို အသုံးချပြီး User မသိဘဲ Action တစ်ခု လုပ်ဆောင်သွားအောင် လှည့်စားတာပဲ။

## 7. SSRF (Server-Side Request Forgery)
SSRF ကတော့ Attacker က Server တစ်ခုကို သူလိုချင်တဲ့နေရာဆီ Request ပို့အောင် လှည့်စားတဲ့ တိုက်ခိုက်နည်းတစ်မျိုးပဲ။

ဥပမာ Website တစ်ခုမှာ Image URL ထည့်လိုက်ရင် Server က အဲ့ဒီ Image ကို Download လုပ်ပေးတဲ့ Feature ရှိတယ်ဆိုပါစို့။

ပုံမှန်ဆို User က Image URL တစ်ခု ထည့်လိုက်တယ်။

Server က အဲ့ဒီ URL ဆီ Request ပို့ပြီး Image ကို Download လုပ်ပေးတယ်။

ဒါပေမဲ့ Website က User ထည့်လိုက်တဲ့ URL ကို သေချာမစစ်ဘူးဆိုရင် Attacker က ပုံမှန် Image URL အစား Server ရဲ့ အတွင်းပိုင်း Network ထဲက Address တစ်ခု ထည့်လိုက်နိုင်တယ်။

ဥပမာ Server ကနေသာ ဝင်ကြည့်လို့ရတဲ့ Internal Service တစ်ခုရဲ့ Address ပေါ့။

အဲ့ဒီအခါ Server က User ထည့်လိုက်တဲ့ URL ကို ယုံကြည်ပြီး အဲ့ဒီ Internal Service ဆီ Request ပို့မိနိုင်တယ်။

ဒီလိုနဲ့ Attacker က အပြင်ကနေ တိုက်ရိုက်ဝင်ကြည့်လို့မရတဲ့ Internal System တွေကို Server ကို ကြားခံအသုံးချပြီး ချိတ်ဆက်ဖို့ ကြိုးစားနိုင်တယ်။

အခြေအနေပေါ်မူတည်ပြီး Internal Data တွေကို ရယူနိုင်တာ၊ Cloud Server ရဲ့ Sensitive Information တွေကို ရယူနိုင်တာ၊ Internal Service တွေကို မလိုလားတဲ့ Request တွေ ပို့နိုင်တာမျိုး ဖြစ်သွားနိုင်တယ်။

ဒီနေရာမှာ မှတ်ထားဖို့က Attacker က Internal Server ကို ကိုယ်တိုင် တိုက်ရိုက် Request ပို့တာ မဟုတ်ဘူး။

ကိုယ့် Website ရဲ့ Server ကိုပဲ သူလိုချင်တဲ့နေရာဆီ Request ပို့ခိုင်းတာပဲ။
### ဘယ်လိုကာကွယ်မလဲ?
User ထည့်လိုက်တဲ့ URL တွေကို Server က တိုက်ရိုက်မယုံကြည်သင့်ဘူး။
Server က ချိတ်ဆက်ခွင့်ရှိတဲ့ Domain တွေကို ဖြစ်နိုင်ရင် ကြိုတင်သတ်မှတ်ထားသင့်တယ်။ (Allowlist)
Internal IP Address, Localhost နဲ့ Cloud Metadata Endpoint တွေဆီ မလိုအပ်ဘဲ Request မပို့နိုင်အောင် ကန့်သတ်ထားရမယ်။
URL ကို စစ်တဲ့အခါ Redirect နဲ့ DNS ပြောင်းလဲမှုတွေကနေ ကာကွယ်နိုင်အောင် သတိထားရမယ်။
Server ရဲ့ Network Access ကို လိုအပ်တဲ့နေရာတွေဆီပဲ ခွင့်ပြုထားသင့်တယ်။

ဥပမာ User က Image URL ထည့်လို့ရတဲ့ Feature တစ်ခုမှာ Server က သတ်မှတ်ထားတဲ့ Image Hosting Service တွေဆီပဲ Request ပို့ခွင့်ရှိအောင် လုပ်ထားမယ်ဆိုရင် SSRF ဖြစ်နိုင်ခြေကို လျှော့ချနိုင်တယ်။

SSRF ကို အလွယ်မှတ်ရရင် ကိုယ့် Server ကို Attacker လိုချင်တဲ့နေရာဆီ Request ပို့ပေးမိအောင် လှည့်စားတာပဲ။
